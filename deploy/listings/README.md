# NASDAQ Trader directory files for the display producer

Trade step: ranking, shown to the owner. The TradingView display producer (`python -m sextant.tradingview.prestage`) builds its universe from NASDAQ Trader's two public directory files, `nasdaqlisted.txt` and `otherlisted.txt`. This user timer stages both files in `$HOME/sextant-data/tradingview-prestage/` on weekdays at 03:00 New York time, before the 04:00 display window. No key, no broker, no TradingView call.

- **Source.** The addresses are the manifest row "REST bar-fidelity display host through the ranking publisher". The format is NASDAQ Trader's [symbol directory definitions](https://www.nasdaqtrader.com/trader.aspx?id=symboldirdefs), read 2026-11-11: "The symbol directory files are updated periodically through-out each day", and "The last row of each Symbol Directory text file contains a timestamp that reports the File Creation Time." The page defines the `otherlisted.txt` Exchange codes A, N, P, Z and V only.
- **Integrity.** `python -m sextant.tradingview.listings DIR` downloads both files, then checks each for UTF-8, the exact header observed on 2026-11-11, the header's field count on every row, at least one row, and the File Creation Time trailer as the last line. A truncated file or an HTML error page fails these checks. Only when both pass is each file replaced atomically (temporary file, fsync, rename), and `listings-receipt.json` records the bytes, SHA-256, row count, File Creation Time and the count of rows with an undocumented Exchange code. On 2026-11-11 the file carried codes F and M, which the page does not define; the producer's parser skips those rows and counts them, and never guesses a venue (`bars.OTHER_LISTED_EXCHANGES`).
- **Failure.** A refused download exits 1. The unit shows `failed`, and the previous good files stay in place. The producer then keeps reading the older files. It does not refuse a stale listing, because no maximum age has a source. Each tick receipt's `universe_source` names both files' File Creation Time, so the age shows in the journal.
- **Restart.** The producer reads the files once, when it starts. After a successful stage, `ExecStartPost` runs `systemctl --user try-restart sextant-tradingview-prestage.service`. It restarts only a producer that is running; at 03:00 that producer is idle between display windows and holds no lease. `Persistent=true` catches a missed run when the user manager returns. If that catch-up comes during a display segment, the restart rebuilds that segment's baseline, one full rebuild of about 16 minutes at 2026-11-11's size; the schedule therefore restarts between segments, never mid-segment.

## Install (the lead, after merge)

1. `bash deploy/listings/install.sh` writes the two units and reloads the user manager. It enables and starts nothing.
2. `systemctl --user start sextant-tradingview-listings.service` stages today's files once. Check them with `journalctl --user -u sextant-tradingview-listings.service -n 5 --no-pager`.
3. `systemctl --user enable --now sextant-tradingview-listings.timer` turns on the daily run.

`parameters.json` records the schedule and the per-request timeout as UNCALIBRATED reused values with their sources. Sources: `deploy/calibration/` (adapted), and [systemd.service](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html) (`ExecStartPost=` runs only after `ExecStart=` succeeds), [systemctl](https://www.freedesktop.org/software/systemd/man/latest/systemctl.html) (`try-restart`) and [systemd.timer](https://www.freedesktop.org/software/systemd/man/latest/systemd.timer.html), read 2026-11-11.
